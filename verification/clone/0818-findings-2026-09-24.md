## (a) 391 attachments ended `failed`

`failed` is the sum of four census statuses: `failed-session`, `inspection-error`,
`unsupported-pack` and `missing-source` (`plugins/sdt-sitter/scheduler.js`,
`SDT_STATUS_CLASSES`, ruled so by ticket 0699). The run recorded no per-status counts.
They are reconstructed here, and the two parts sum to exactly the toast's 391:

- **367 `missing-source`.** These are in-scope attachments (PDF, EPUB or snapshot, not
  trashed) whose file does not exist. The count is the same on the pristine copy and after
  the run, so the run did not cause it. By Zotero's own sync state
  (`SYNC_STATE_TO_DOWNLOAD` = 1, `IN_SYNC` = 2):
  - 178 are in the two group libraries at state 1. Zotero knows these files are on the
    server and has not downloaded them.
  - 186 are in the user library at state 2 with no file (183 of them with no storage
    directory at all).
  - 3 are linked files at absolute paths under `/home/haduong/` that no longer exist.

  This is a property of the source library. The copy holds exactly what doudou held;
  the sitter did not lose anything.
- **24 `failed-session`.** The sitter emitted 24 `settle` events with `ok: false`,
  and none of them had a pack before the run. 23 of the 24 already appear in the
  author's own error history from 2026-09-06 (`sdt-sitter-errors.jsonl`, a channel
  retired since, which is why the run appended nothing to it). There, 15 in the user
  library had already failed native extraction ("did not persist a current pack"), and
  8 in group 3 had failed earlier, at a title read. By content:
  - 18 are real PDFs, most of them attached in both the user library and group 3.
  - 6 are labelled `application/pdf` but are empty (2) or HTML (4).

  The sitter records only the error class (`Error`), not the message. **Not
  established:** why native extraction rejects the 18 PDFs.

  **The one experiment that settles it:** in a reflink arena on padme, call
  `Zotero.SDT.ensure()` on `1/J2XJRQXE` with debug output on, and read the message
  the worker throws.

  A small, separate gap: the pre-extraction byte sniff already turns a mislabelled
  `.zip` into `unsupported / mismatched-type`. It returns nothing for an empty or HTML
  file, so those 6 reach the native worker every session.

## (b) 8 035 existing packs rewritten on the first run

Every pack present before the run was decoded: header, and its raw-deflated metadata.

| Before the run | Count | Run's verdict |
|---|---:|---|
| processor `pdf@3`, schema 1.1.0 | 8 028 | rewritten |
| processor `epub@1`, schema 1.1.0 | 7 | rewritten |
| current (`pdf@14`, or `snapshot@1`), schema 1.1.0 or 1.2.0 | 5 672 | kept, byte-identical |
| `pdf@3` label on a `.zip` file | 2 | kept (`unsupported`, never queued) |

The run's Zotero 10.0.3 declares `pdf` 14 and `epub` 2. These are the constants whose
move from pdf 3 / epub 1 (Zotero 10.0) is recorded in `SYNC.md`'s extraction row.
Zotero's own validity check compares `processor.version`, so each of the 8 035 is a
`stale-processor` pack. `ensure()` regenerates it before resolving, and the sitter's
census calls `ensure()`. `completed` 8 103 = 8 035 rewritten + 68 new packs, exactly.
In all 8 035, the stored source hash equals the file's MD5, so the processor version
is the only stale field.

The legacy cache played no part in the choice. The pristine `sdt-sitter-cache.jsonl`
has 5 672 rows, all written without the `format` stamp that ticket 0771 added, so the
run loaded none of them (`cache-load {"records":0}`) and re-read every pack. A cache
miss costs a read, not a rewrite. The legacy rows cover exactly the 5 672 current
packs, and not one stale pack.

What this means for a live install: the author's library was last opened by 10.0.3
(`settings.lastVersion`), so the same verdict applies on doudou. The first live run
will regenerate about 8 000 packs, which took 20 910 s (5,8 h) on padme. Not
established: whether doudou still holds them all today, since native Zotero also
regenerates a stale pack when a reader opens it. `bench/pack_census.sh` on doudou
answers that before an install.
