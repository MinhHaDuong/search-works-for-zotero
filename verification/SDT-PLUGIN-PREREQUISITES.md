# Native SDT pack sitter: prerequisite audit

Date: 2026-09-05. Evidence for ticket 0673, not a new system specification.

## Verdict and scope

A plugin can drive Zotero's own pack generation without changing full-text
preferences, bundling an extractor, or keeping a private success database.
The native service is sufficient for a bounded prototype. It is NOT sufficient
to promise non-interference, immediate cessation on disable, or recovery from
a hung worker. Unattended library-wide activation is not cleared by this audit.

The installed application on doudou is Zotero 10.0.1, build 20260824184709.
Source was read directly from `/opt/zotero7/app/omni.ja`, especially
`chrome/content/zotero/xpcom/sdt.js`, `pdfWorker/manager.js`, and
`resource/document-worker/worker.js`. The service digest and processor metadata
are recorded in `bench/results/sdt-prerequisites-2026-09-05/service-contract.json`.
No claim of latest upstream currency or padme installation compatibility is made.

`verification/probes/sdt_service_contract.mjs` executes the actual installed
service in a Node VM with simulated host, storage, parser and worker. The raw
result names every passing scenario. This validates service control flow, not
real PDF extraction, binary-pack parsing, filesystem atomicity, privileged
Gecko APIs, or actual concurrent Zotero usage. Reproduce with:

```sh
node verification/probes/sdt_service_contract.mjs /opt/zotero7/app/omni.ja
```

The sandbox refused Node's subprocess operation; the successful run used an
approved local execution. It did not connect to the running application.
Separately, a read-only live check found Zotero's existing full-text endpoint
responsive and its submitted-job counter idle. This is not proof that its
reader or SDT worker is idle. Storage was readable with free space; the host
also had little free swap. Neither observation certifies future resource safety.
No pack generation, plugin installation, preference change or restart occurred.

## Native contracts verified

| Prerequisite | Finding | Limit |
|---|---|---|
| Generation entry point | `Zotero.SDT.ensure(itemID, {isPriority:false, onProgress})` resolves true only after a current cache is available | Internal API; require capability checks and a tested version range |
| Supported sources | PDF, EPUB and saved snapshots with readable local files | Linked URLs, missing files and unsupported attachments cannot be packed |
| Cache identity | Source hash, processor type/version, pack version and schema major are checked | Hash reuse assumes unchanged path, size and mtime imply unchanged bytes |
| Cache location | `Zotero.Attachments.getStorageDirectory(item)` owns the pack location | For linked files, do not assume it is beside the source PDF |
| Cache hit | Does not run the extractor or rewrite the pack | It reads the whole pack; a cold sweep also hashes source files |
| Concurrent consumers | Per-library/item generation is deduplicated; progress listeners join the same job | A later priority consumer does not upgrade the already queued generation |
| Progress | Shared generation callbacks are available | Final progress precedes validation and disk write; only successful resolution completes the job |
| Source edit while running | Generated bytes are checked against a refreshed source hash | Tested with a changed file stat; not arbitrary concurrent-file mutation detection |
| Persistence | Service validates the returned pack, then writes using a temporary path | The mock verifies arguments/order, not crash durability or disk-full behaviour of Gecko |
| Errors | Service resolves false on generic failures; password failures are remembered for the session | `ensure` discards the reason; generic failures retry on every new call |

The installed worker has no page-cap argument on the SDT path. Existing evidence
for an uncapped book is in `verification/SDT-CAPS-0483.md`. Therefore lifting
Zotero's full-text preferences is unnecessary for this plugin and would activate
an unrelated full-text workload. A valid pack is not proof of perfect extraction:
OCR gaps and degraded layout extraction must not be presented as complete text.

## Load-bearing risks

### Scheduling and disable

`PDFWorker` uses a shared serial queue. Priority orders waiting jobs, not running
jobs. The sitter can stop admitting attachments; it cannot yield an admitted
large attachment when the reader, import or native indexing needs the worker.
The previous live flat-text experiment demonstrated head-of-line blocking in
this arrangement: `verification/INDEX-SITTER-LIVE.md`.

Neither `SDT.ensure` nor the installed worker accepts an abort signal. Plugin
shutdown cannot retract the submitted job or its eventual cache write. Shutdown
must remove timers, observers and windows and invalidate callbacks, but that is
not cancellation. Disabling/re-enabling during a job also needs an integration
test for old callbacks and duplicate schedulers.

The worker's error event only logs; pending query promises are not rejected by
that handler. A worker crash can therefore strand the awaited job. A watchdog
can report lack of progress and stop admissions, but must not claim to repair
it, time out and resubmit, or terminate Zotero's shared worker. A healthy large
job and a hang cannot be distinguished reliably by duration alone.

### Census, failures and state

There is no public read-only SDT status method. `getPack` can regenerate in the
background; `getReader` calls it; `ensure` can generate and reduces errors to a
boolean. None is suitable for a passive statistics refresh or an admission
preflight that promises not to start work.

An inspector would have to use the bundled pack reader against cache files,
maintaining a small compatibility layer and checking provenance. The absence
of such an inspector is a prerequisite for the automatic version, not a reason
to call `ensure` over the whole library as a cheap census. Census must enumerate
attachments independently of native full-text coverage and retain library/item
identity. Missing local files and linked-file cache paths must be tested.

Successful progress can be reconstructed from native packs without private
durable state. Session-local failure suppression is still needed: generic
failures are not suppressed by the native service. With no durable error ledger,
restart forgets failure history and empirical ETA; the UI must disclose that.
Detailed error reasons require an additional observable surface; do not label
all false results as password failures or use `getPack` as a harmless error query.

### Resource and performance prerequisites still open

The installed inference explicitly selects WASM with a single thread and SIMD;
model sessions select the WASM execution provider. A native inference bridge is
present in the worker but not activated by the installed manager. The sitter
alone does not enable multicore inference or either GPU. It must not change the
process-wide priority of Zotero to make just its own workload nicer.

Source buffers, generated packs and validation bytes can overlap in memory.
Temporary replacement also needs disk space in the actual cache filesystem.
Free disk/memory checks are admission hints, not a reservation or a guarantee
that an admitted job cannot exhaust resources. Platform resource APIs, writable
cache directories, low-space refusal and memory-pressure behaviour remain to be
verified inside Zotero on each target host. CPU count is not free CPU capacity.

Pack generation remains independent of native full-text indexing. Existing
full-text statistics may be displayed separately, never relabelled pack coverage.
The Zoteus checkout still consumes flat text; producing packs is not the same
as making Zoteus consume them. The source-selection deployment checkpoint in
SPEC.md remains unchanged by this audit.

## Bounded next validation

The next implementation step is a diagnostic plugin exercised in an isolated
profile with disposable fixture attachments, not an automatic production sweep.
It should establish the actual in-process capability and storage checks; passive
inspection without cache writes; a current-cache hit; a missing/stale-pack
generation; progress through persistence; coexistence with a reader request;
failure suppression; and complete lifecycle cleanup on disable/re-enable.
No production HTTP mutation surface is required for the eventual toolbar plugin.

Before library-wide activation, resolve the product boundary explicitly:
accept best-effort admission with uninterruptible in-flight work, or require an
upstream yield/cancel facility or an isolated extraction architecture. This
audit does not silently weaken the author's non-interference requirement.
