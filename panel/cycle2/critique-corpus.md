## FATAL

### F1. The reference-only passage store has no text source for the semantic core (phases A and A′)

B2 declares "passages store references, not text": every `passages` row is `(sid, off_start, off_end, fp)` into a slab, FTS goes contentless, and the snippet path is gunzip-slice-verify. B2's slabs are defined as spans of "the attachment's extracted text" (`slabs.attachment_key`, `char_start/char_end`). But the rows the rulings care most about — **record rows (phase A) and own-words rows (phase A′)** — have no attachment and no extracted text. There is no slab for a title/abstract/tags record, none for a note, none for an annotation. So for the corpus class the record ruling makes "the first 100%", the schema as written cannot: (a) render a snippet (B7's hit shape promises one), (b) verify a fingerprint ("null text rather than the wrong words" has no bytes to check), or (c) honor the delete protocol's "single text copy to purge" — because there is *zero* copy. Concrete failure state: minute 9 of a fresh build, phase A complete, an agent queries; every hit is a record hit; every snippet is underivable. Either the implementation quietly stores record/note text somewhere (contradicting the single-copy claim B2 uses to book the 0.65 GB saving and the one-transaction R15 story), or the flagship answer of the first 100% ships blank. The memo never notices because its snippet arithmetic only exercises body rows.

**Cheapest repair:** extend the slab store beyond attachments — `slabs.source ∈ {attachment, record, note, annotation}` keyed by item/note key, with record and own-words text slabbed exactly like body text (tiny slabs, same gunzip path, same fp, same delete transaction). One column and one sentence; but it must be written, because as specified the schema rejects phases A/A′ at the type level (`passages.sid` has nothing to point at).

## MAJOR

### M1. The disk arithmetic contradicts itself, and quotes old-geometry passage counts for a new-geometry design

B2: "v1 = FTS (~0.5) + passages text (~0.68) + gzip slabs (~0.23 at 3:1) + vectors (0.25) + metadata ≈ 2.3 GB (v1 §2.9's own figure)." Those components sum to **1.66 GB**; reaching 2.3 requires ~0.64 GB of "metadata", which is absurd. What actually happened: v1 priced slabs at **0.7 GB** (its own §2.9 line — apparently uncompressed), the memo silently re-priced them at 0.23 GB gzipped, and then kept v1's 2.3 total as the baseline anyway. So "2.3 → 1.6–1.7" subtracts the right delta from the wrong base. Recomputed with the memo's own component prices, the new design is ~0.5 + 0.23 + 0.25 + ~0.1–0.15 ≈ **1.1–1.2 GB**, not 1.6–1.7. Second layer of the same defect: all of it assumes 650k passages at the *old* 1200-char chunker, while B4 adopts 768-token (~3,000-char) chunks — the same corpus yields roughly 250–300k passages, shrinking the vector sidecar to ~0.1 GB and the FTS index too. The error is favorable in direction both times, but a memo whose lens is corpus arithmetic failed the recompute-everything standard on its own headline number. **Repair:** redo §B2's table once from the token geometry; state both passage counts (old-geometry for bench comparability, new-geometry for the budget).

### M2. Census-intersect has its own blind spot: 0 == 0, and the memo asserts it away

B6 closes with "version 0 (local extraction) is just a value that either equals the stored one or doesn't." That is precisely the failure: **a local re-extraction of an already-version-0 attachment produces 0 again** — equality holds, no enqueue, stale text served indefinitely. The 0012 artifact shows the living library has multiple version-0 entries (`fulltext_version_min: 0`), and a never-synced library is *all* zeros — for that user the entire fulltext-freshness protocol degrades to "detect first extraction only." The scout finding the memo cites ("equality-comparable per item") licenses equality for *stamped* versions; it does not make 0 a usable value, and SYNC §4's open question (does re-extraction bump anything observable?) is exactly this hole, unmeasured. C1's claim that Zotero "bumps on re-extraction" and the scout's "0 for local extraction" are in tension, and the memo resolves the tension by not mentioning it. Even Zotero accepts a staleness residue here (SCOUTS: processor-bump-without-file-change is deliberately not chased) — so the honest design says so. **Repair:** name the residue in B6 and in the coverage contract ("version-0 text is refreshed only on file change or manual rebuild"), and note that Issue-2's answer decides whether a periodic content-hash spot-check of version-0 keys is needed. No silent-wrongness allowed by C2.

### M3. The schema has no library column — D4-merged makes key collisions corrupting

D4 resolved **merged**: one index spanning personal + groups, and R12 binds "indexing one library never erases another." Zotero object keys are unique *per library*; personal `ABCD2345` and group `ABCD2345` are different objects that can and do coexist. B2's `entries/slabs/passages` carry `item_key`/`attachment_key` with no library discriminator, and B6 partitions by `Zotero-Server-ID` only — which separates *profiles*, not the libraries within one profile. Failure state: group item and personal item share a key; R15's one-transaction delete for the personal item purges the group item's entries, slabs, and FTS rows — the exact erasure R12 forbids, silent. Upstream's own #12 work (groups servable) makes this a live configuration, not hypothetical. **Repair:** `library_id` on every table, in every unique key, and in the delete predicate. One column; but sheet-binding, and the memo's schema is the artifact the RFC will copy.

### M4. The JS-bitmap filter can serve a false "nothing matches in this scope" — an R5/R18 violation the memo builds in

The kill of "join the predicate into MATCH" is correct (scout-measured; upstream already unconstrained at `sqlite-index.ts:178-184`). But the replacement — pool = limit×6, "enlarged when a filter is active", bitmap-filtered in JS — is post-filtering a top-k, which is the letter of what R5 forbids, and it fails concretely: query "economie" scoped to a 200-item collection; the dictionary's entries plus the statistical yearbooks (0013's top items) fill all 60 pool slots; zero survive the bitmap; R18 dutifully reports "no matches" *with entry coverage confirmed* — a coverage-honest lie, worse than today's, because the sentence now claims authority. Enlargement is a heuristic; correctness needs a guarantee. **Repair (cheap):** page the unconstrained MATCH — keep pulling ranked candidates (OFFSET or rank-keyset continuation) until `limit` allowed hits are found or FTS is exhausted, with a disclosed work cap. Three lines of loop; the memo wrote none of them, and R18's promise depends on it.

### M5. "Content-addressed vectors" is ambiguous where it matters, and its R11 benefit is overstated

B4 keys vectors by `(chunk_content_hash, embedder_key)` and claims a segmenter bump "re-embeds nothing" for reproduced chunks. But B3 defines the *embedded* text as `«item title» › «heading path» ¶ «chunk text»`. If the hash covers chunk text only, two chunks with identical bodies but different headings share one vector — a vector computed under the *old* heading serves under the new one: silently wrong embeddings, the exact defect class R11 exists to prevent, now unobservable. If the hash covers the full embedded text (the only correct choice), then a segmenter bump — whose entire purpose is to change cut points and headings — changes the prefix and re-embeds most of what changed; the "embed-cheap re-index" claim in (c) shrinks to "chunks in regions the segmenter didn't touch." Additionally, shared hashes across items make R15's one-transaction vector delete unsafe without a refcount/EXISTS guard (delete item A's vector, orphan item B's chunk). **Repair:** define the hash over the full embedded text; add the EXISTS guard to the delete; restate the R11 claim honestly ("unchanged regions never re-embed" — still valuable, no longer magic).

## MINOR

- **m1.** The tick now performs a full `/fulltext?since=0` census *per tick* (60 s cadence in v1 §2.5): ~8,037 entries ≈ hundreds of KB per minute, forever. Legal on the local API (no limits, unpaginated), but on the **web transport** — which upstream supports and where versions *are* monotonic server stamps — this is O(library) polling where a cursor is safe and the politeness constraint (≤4 concurrent, Backoff) makes it rude. The memo imposes census-intersect universally without a transport split.
- **m2.** K=64 band cap inherited unmodified: it was "one median item" at 63 passages/item under the 1200-char chunker; under 768-token chunks the median item is ~25 passages, so K=64 is now ~2.5 items' worth. Needs re-derivation, not transplant.
- **m3.** "~1,850 entries" for the Palgrave is presented as arithmetic input but is an unlabeled external assumption (no bench artifact carries it). The downstream numbers (24 KB, 6k tokens, 8–9 chunks) are internally consistent *given* it.
- **m4.** "Notes invisible" overbroad — standalone notes are indexed today (`d.note` in `itemText` + `top:true` returns top-level notes). Child notes and annotations are the real gap; the fix (PR-c) stands either way, but PR-c's "second non-`top` pass" will re-crawl every attachment unless itemType-filtered — say so or the PR is heavier than "contained."
- **m5.** B3's bm25 weights are "tuned against R21's golden set" while confession 3 admits the golden set is item-denominated and needs entry-level re-pinning — the tuning instrument doesn't exist until the manual work the memo "schedules but cannot do" is done. The weights ship untuned or the RFC waits.
- **m6.** B3's "any phrase ≤ 48 tokens survives a chunk boundary" is misstated: Zotero's geometry overlaps only within a *split paragraph*; paragraph-boundary cuts have zero overlap. The conclusion still holds (sentences don't span paragraphs, cuts don't split sentences) — the stated reason is wrong, the right reason should replace it.

## SURVIVED ATTACK

- The kill of v1's two-column `meta_text` FTS: with `'. '`-joined fields, unicode61 treats `.` as a separator, so "Smith. climate" tokenizes to adjacent positions and the quoted phrase matches across the seam — a real, demonstrable D5 violation; per-field columns fix it structurally and the ruling demands them. Verified, and the replacement is strictly better.
- The kill of v1's ascending `/fulltext` sweep — the mixed-sequence scout finding is decisive; only `since=0` is safe on the local transport (0012's data shows the mixed range 0..25,036 live).
- The kill of v1's collapse-to-item: ruling-mandated, and entry-MAX + item grouping is not worse than the disease (D9 dissolved by the author's own words).
- The phase order (records → own-words → body) is the record ruling verbatim; phase-A arithmetic (12–15k chunks / 25 s⁻¹ = 8–10 min) is internally consistent and its one assumption is labeled.
- R14 done-state vs quarantine, with D8 leave-room via extractor id: clean, mechanism-sharing, correct bookkeeping distinction.
- All ten ground-truth citations, the ~1000-fold truncation figure, and the newest-first-vs-smallest-first divergence being *documented as a decision* rather than assumed.

## CONFESSIONS, JUDGED

Confession 1 (segmenter unmeasured) is the genuine top risk and no decoy — silent plausible-wrong entries poison locators *and* dedup units, and the falsifier is correctly scheduled before the RFC. Confession 2 confesses gunzip *latency* while missing that record/note rows have no gunzip *source at all* (F1) — a decoy in exactly the sense the standard warns about: the confessed weakness sits beside the bigger hole in the same subsystem. Confession 3 is real and honest.

## VERDICT

The memo's factual layer is the best-verified of the cycle: every citation held. Its kills of v1 are all justified. Its failures are all in the new construction: a schema that forgot the semantic core needs text too (F1), a budget line that fails its own recompute (M1), a freshness protocol that hides its residue (M2), a merged-index schema without the merge key (M3), a filter path that can lie in scope (M4), and a caching claim whose key is undefined at the decisive point (M5). Every repair is cheap and named; none is optional.
